\chapter{Reading and Writing}\label{ch-reading-writing}

A program is more useful when it can take something in and leave
something behind: lines typed at a keyboard or sent down a serial
line, words on the command line, files on a disk. This chapter covers
all three, and JSON, the text that programs hand each other. \verb|print| has been with us since the first page.

\begin{center}

\midrule

\section{print}

\verb|print| shows its values on one line, with a space between them,
and ends the line. Text is shown as it is; inside a list, it is shown
in quotes. To lay a line out exactly, build it with an \verb|f| string
(\hyperref[ch-text]{Text}):

\begin{zeno}
let volts = 3.3
print("supply", volts, ["a", 1])
print(f"supply={volts:.2f}V")
print()
print("after an empty line")
\end{zeno}

\section{Reading lines: input}

\verb|input()| reads the next line, without its line end. Given a
question, it prints the question first and stays on that line. When
there are no more lines, it gives \verb|none|: at a keyboard that is
Ctrl-D (Ctrl-Z then Enter on Windows), and for a file sent in with
\verb|<| it is the end of the file.

\begin{zeno}[stdin=Ada\n]
let name = input("Name: ")
if name is none {
    print("nobody there")
} else {
    print(f"Hello, {name}!")
}
\end{zeno}

Here the line \verb|Ada| was sent in rather than typed, so it does
not appear after the question as it would at a keyboard.

Because the answer may be \verb|none|, it must be asked about before it
is used as text (\hyperref[ch-none]{Values That May Be Missing}). A
loop that reads every line breaks on \verb|none|, and after that the
checker knows the line is a \verb|str|:

\begin{zeno}[stdin=12\n7\nfast\n30\n]
var total = 0
while true {
    let line = input()
    if line is none {
        break
    }
    try {
        total += int(line.strip())
    } except ValueError {
        print("not a number:", line)
    }
}
print("total", total)
\end{zeno}

Here the program was given four lines. Run it yourself and type them,
or put them in a file and send it in: \verb|zeno run total.zeno < numbers.txt|.

\begin{why}
Python's \verb|input()| raises an error at the end of the input, so a
loop that reads everything needs a \verb|try|. \verb|none| is the
answer "there is no line", and the type makes sure the program
handles it. (Decision 6.18.)
\end{why}

On a board, a firmware C library usually ties the input to a serial
line, and then \verb|input()| reads a line from the serial port.

\section{The command line}

\verb|program.arguments()| gives the words written after the file, as
a list of text. The program's own name is not in it, so the first
word is \verb|[0]|:

\begin{zeno}[file=greet.zeno, args=Ada Grace]
import program

let names = program.arguments()
if len(names) == 0 {
    print("usage: zeno run greet.zeno <names>")
}
for name in names {
    print("hello,", name)
}
\end{zeno}

With \verb|zeno run|, every word after the file belongs to the
program, even one that looks like an option of Zeno's; Zeno's own
options go before the file: \verb|zeno run --vm greet.zeno Ada|. A
compiled program gets the same list from the words after its name:
\verb|./greet Ada Grace|.

\section{Ending, warning, and the environment}

A program that other programs call says how it went with a number
when it ends: 0 if all went well, anything up to 255 if not. A script
reads that number with \verb|&&|, \verb|||| or \verb|$?|.
\verb|program.exit(code)| ends the program there with that number.
It is not an error, so no \verb|try| stops it. \verb|program.warn|
writes a line on the error stream, which the shell keeps apart from
what \verb|print| prints, so a complaint does not end up in a file
the output was sent to:

\begin{zeno}[file=hello-all.zeno, fails=yes]
import program

let names = program.arguments()
if len(names) == 0 {
    program.warn("usage: zeno run hello-all.zeno <names>")
    program.exit(2)
}
for name in names {
    print("hello,", name)
}
\end{zeno}

A number outside 0 to 255 is a \verb|ValueError|: on Linux,
\verb|exit(256)| would arrive as 0, a failure that looks like a
success.

\verb|program.environment(name)| reads the environment the program
was started in, the names and text a shell sets, such as
\verb|HOME|. It gives \verb|none| for a name that is not set, which
the program must look at before it uses the text:

\begin{zeno}[run=no]
import program

let home = program.environment("HOME")
if home is none {
    print("no home folder")
} else {
    print("home is", home)
}
\end{zeno}

A firmware build refuses \verb|program.environment|: a board has no
environment. Chapter 34 of \texttt{docs/decisions.md} gives the
reasons for all three.

\section{Files}

\begin{zeno}
import files

files.write("shopping.txt", "milk\neggs\n")
files.append("shopping.txt", "bread\n")
print(files.read("shopping.txt").lines())
print(files.exists("shopping.txt"))
files.remove("shopping.txt")
print(files.exists("shopping.txt"))
\end{zeno}

A file is read whole, as one \verb|str|, and written whole. There is
no \verb|open| and no \verb|close|, so there is nothing to forget to
close. \verb|write| makes the file, or empties it first;
\verb|append| makes it, or adds to its end.

\verb|write| and \verb|append| put down exactly the text they are
given. A program that wants lines ends each with \verb|"\n"|, and
reads them back with \verb|lines()|, which knows both kinds of line
end, so a file from Windows reads the same.

\begin{why}
Opening and closing is a pair that every program must get right on
every path, errors included, and a file left open is a classic leak.
Reading and writing whole files covers what most programs do, with no
pair to get wrong. A large file, read in pieces, needs a file that
stays open; that is the next section but one, where the pair is kept
by the end of a block and not by the program. (Decisions 6.12, 6.13
and 59.6.)
\end{why}

\subsection{When a file cannot be used}

A file that cannot be used raises a \verb|FileError|, with a message
that says why:

\begin{center}
\begin{tabular}{ll}
\toprule
What happened & The message \\
\midrule
nothing is at the path & \verb|there is no file `notes.txt`| \\
it is a folder, or may not be read & \verb|cannot read `notes.txt`| \\
it is not text & \verb|`notes.txt` does not hold text| \\
it cannot be made or written & \verb|cannot write `notes.txt`| \\
it cannot be removed & \verb|cannot remove `notes.txt`| \\
\bottomrule
\end{tabular}
\end{center}

\begin{zeno}
import files

function first_line(path: str) -> str raises FileError {
    let lines = files.read(path).lines()
    if len(lines) == 0 {
        return ""
    }
    return lines[0]
}

try {
    print(first_line("settings.txt"))
} except FileError as e {
    print("no settings:", e.message)
}
\end{zeno}

A missing file is not a mistake in the program: no check the program
could make beforehand rules it out, since another program may remove
the file in between. So \verb|FileError| can always be caught, even in
a firmware build where other errors stop the program. A function that
uses a file says \verb|raises FileError|, or catches it.
(Decision 6.14.)

\subsection{A file holds text}

\verb|files.read| gives a \verb|str|, and a \verb|str| is characters,
so the file must be UTF-8 text. A picture or any other bytes are
refused with a \verb|FileError|.

\subsection{Bytes}

A file that is not text, such as a firmware image or a record a board
wrote, is read with \verb|files.read_bytes|. It gives every byte of the
file, as it is, in a \verb|list[u8]|: each byte is a number from 0 to
255, and the list does all a list does. \verb|files.write_bytes| makes
a file, or replaces what it held, with one byte for each item:

\begin{zeno}
import files

let frame: list[u8] = [0x7E, 0x01, 0x00, 0xFF]
files.write_bytes("frame.bin", frame)

let back = files.read_bytes("frame.bin")
print(len(back), back)
var sum = 0
for byte in back {
    sum = (sum + byte) % 256
}
print(sum)

files.write("name.txt", "é")
print(files.read_bytes("name.txt"))
files.remove("frame.bin")
files.remove("name.txt")
\end{zeno}

The last lines show that text is stored as UTF-8: one \verb|é| is two
bytes. The list given to \verb|write_bytes| is a \verb|list[u8]|, so
every item fits in a byte; a number written out that does not, such as
\verb|256|, is refused before the program runs, and a \verb|list[int]|
is refused too, because it could hold anything. Write
\verb|[u8(n) for n in numbers]| to say where the check is made. The
errors are those of \verb|files.read|: no file, or one that cannot be
read. (Decision 36.1.)

\section{Folders}

\verb|files.make_folder| makes a folder, and every folder above it
that is not there yet. \verb|files.list| gives the names in a folder,
and \verb|files.join| puts a folder and a name together into a path:

\begin{zeno}[file=logs.zeno, dir=folders]
import files

let day = "logs/2026/november"
files.make_folder(day)
files.make_folder(day)
files.write(files.join(day, "20.txt"), "temp 23.5\n")
files.write(files.join(day, "9.txt"), "temp 21.0\n")
files.write(files.join("logs/2026", "Notes.txt"), "calibrated\n")

print(files.list("logs/2026"))
for name in files.list(day) {
    let path = files.join(day, name)
    print(path, files.read(path).strip())
}
\end{zeno}

Making a folder that is already there is no error: what counts is
that there is a folder at the path at the end. So a program can make
its folders each time it starts, without asking first. Something else
in the way, such as a file, is a \verb|FileError|.

\verb|files.list| gives the names of everything in the folder, files
and folders alike, as a \verb|list[str]|. A name is only the last
part of the path, \verb|"20.txt"| and not
\verb|"logs/2026/november/20.txt"|, and \verb|files.join| puts the
two back together. To tell a folder from a file, ask
\verb|files.exists|, which is true only for a file.

The list is sorted in the order \verb|<| gives two texts, by the
numbers of the characters. So \verb|"20.txt"| comes before
\verb|"9.txt"|, since the character \verb|2| comes before \verb|9|,
and \verb|"Notes.txt"| before \verb|"november"|, since capitals come
before small letters. A program that wants another order sorts the
list itself.

\begin{why}
A system gives the names in a folder in an order of its own, and not
the same one on Linux, on Windows or on a board's card. A program that
printed them as they came would print something different from one
machine to the next, and a test of it could not be written once. The
order a person would sort in, with \verb|"9"| before \verb|"10"|,
depends on a language and on the machine's settings. The order of
\verb|<| is the same everywhere. (Decision 59.20.)
\end{why}

\verb|files.join| puts one \verb|/| between the two parts, whatever
their ends hold. An empty first part is no folder, and the second
comes back as it is:

\begin{zeno}[file=paths.zeno, dir=folders]
import files

print(files.join("logs", "today.txt"))
print(files.join("logs/", "/today.txt"))
print(files.join("", "today.txt"))

try {
    print(files.list("no-such-folder"))
} except FileError as e {
    print(e.message)
}
files.write("notes.txt", "")
try {
    files.make_folder("notes.txt/old")
} except FileError as e {
    print(e.message)
}
files.remove("notes.txt")
\end{zeno}

The path uses \verb|/| on Windows too, which every system Zeno runs on
takes, so a program that prints a path prints the same text on every
machine. \verb|join| does not look at the disk, and takes two parts
only: for three, write \verb|files.join(files.join(a, b), c)|. A board
has no folders, so there \verb|files.list| and
\verb|files.make_folder| raise a \verb|FileError|, which the program
can catch; \verb|files.join| works anywhere. There is no way yet to
remove a folder. (Decisions 59.21 to 59.23.)

\section{A file in pieces}

\verb|files.read| reads a whole file into one text. A log of a
gigabyte, or a file that grows while the program runs, wants a line
or a few bytes at a time. \verb|files.read_from| opens a file to be
read in pieces, and \verb|files.write_to| one to be written so:

\begin{zeno}[file=errors.zeno, dir=pieces]
import files

files.write("big.log", "boot\nerror: no card\nready\nerror: low battery\n")

let source = files.read_from("big.log")
let errors = files.write_to("errors.log")

for line in source {
    if line.starts_with("error") {
        errors.write(line + "\n")
    }
}
print(files.read("errors.log"))
\end{zeno}

\verb|errors.log| was read while \verb|errors| was still open, and it
held both lines already: every \verb|write| hands its text to the
system before it gives back, so a write that cannot be done is a
\verb|FileError| at that \verb|write|, where it can be caught. There
is no \verb|close|. A \verb|files.Reader| and a \verb|files.Writer|
are resources (\hyperref[ch-ownership]{Ownership}), so the file is
closed when the \verb|let| that holds it, or the parameter that took
it, ends: at the end of its block, at \verb|return| or \verb|break|,
or as an error goes past. Here that is the end of the program.

What a reader and a writer can do:

\begin{center}
\begin{tabular}{ll}
\toprule
Write & Does \\
\midrule
\verb|reader.read_line()| & the next line without its line end, or \verb|none| after the last \\
\verb|reader.read_bytes(count)| & up to \verb|count| bytes, as a \verb|list[u8]| \\
\verb|for line in reader| & each line in turn \\
\verb|writer.write(text)| & writes the text, and adds no line end \\
\verb|writer.write_bytes(bytes)| & writes the bytes \\
\bottomrule
\end{tabular}
\end{center}

\verb|files.append_to| writes after what the file already holds, and
makes the file if it is not there. A line ends at \verb|"\n"|, and a
\verb|"\r"| just before it goes with it, as \verb|lines()| reads it.
In a \verb|for| the loop holds one line at a time, and after a
\verb|break| the reader goes on from where it stopped. The reader must
have a name: \verb|for line in files.read_from(path)| is refused,
because nothing would own the file to close it.

The end of a file is where it ends at that moment. A read that found
the end looks again the next time, so a reader follows a file that
this program, or another, is still writing:

\begin{zeno}[file=grow.zeno, dir=pieces]
import files

let out = files.write_to("grow.log")
let source = files.read_from("grow.log")
print(source.read_line())
out.write("one\n")
out.write("two, still being written")
print(source.read_line())
print(source.read_line())
print(source.read_line())
\end{zeno}

What is there without a line end is given as a line, as the last line
of any file is. The reader does not wait for more: when nothing new is
there it gives \verb|none|, and the program decides when to look
again.

A program cannot make a reader itself, \verb|files.Reader(...)|, nor
read from a writer or close either by hand; to close one sooner, give
it to a function that takes it. With no collector a line is built in
the text room, as \verb|input()| builds one, so a line longer than the
room stops the program with the room's message; \verb|read_bytes|
takes its list from the pool instead. A \verb|FileError| that nothing
catches names a line of \verb|library/files.zeno|, where the reader
is written in Zeno, and its message names the file.

\begin{why}
An open file is the pair this chapter kept away from: open and close,
right on every path. A resource keeps the pair for the program: the
close is at the end of the block that holds the file, which the reader
can see, and an error cannot jump over it. Writing each piece through
to the system at once means an error comes at the \verb|write| that
caused it, where the program can catch it, and not at a close where it
would have nowhere to go. The reader and writer are written in Zeno
over six small built-ins, so a program that never reads a file in
pieces carries none of it. (Decisions 59.6 and 59.7; new in 0.8.)
\end{why}

\section{A worked example: a log book}

This program keeps a log of readings in a file. Each run adds the
readings given on the command line, then prints every reading so far
and their average:

\begin{zeno}[file=logbook.zeno, cmd=zeno run {file} 21.5 22.0 ;; zeno run {file} 23.5]
import files
import program

let path = "readings.txt"

for word in program.arguments() {
    try {
        let value = float(word)
        files.append(path, f"{value}\n")
    } except ValueError {
        print("skipped:", word)
    }
}

var values: list[float] = []
if files.exists(path) {
    for line in files.read(path).lines() {
        values.append(float(line))
    }
}
print(len(values), "readings:", values)
if len(values) > 0 {
    print(f"average {sum(values) / float(len(values)):.2f}")
}
\end{zeno}

\section{JSON}

Programs hand each other text in one format more than any other:
\emph{JSON}. A server answers in it, and a program keeps its settings
in it. The \verb|json| module reads it and writes it, with two
functions: \verb|json.parse(text)| gives the value the text
describes, and \verb|json.write(value)| gives a value as JSON, on one
line.

\begin{zeno}[file=settings.zeno, dir=json]
import json

let text = "{\"name\": \"pump 2\", \"limit\": 80, \"alarms\": [\"high\", \"dry\"]}"
let settings = json.parse(text)
let name: str = settings["name"]
let limit: int = settings["limit"]
print(name, limit + 5)
for alarm in settings["alarms"] {
    print(alarm.upper())
}
\end{zeno}

Each kind of JSON value becomes a value Zeno has: an object a dict, an
array a list, text a \verb|str|, \verb|true| and \verb|false| a
\verb|bool|, and \verb|null| \verb|none|. A number with nothing after
its point is an \verb|int|, even written \verb|12.0|, because many
programs write a whole number either way and mean nothing by it;
write \verb|float(x)| where a \verb|float| is wanted whatever came.
A member that is \verb|null| is left out of the dict, since a dict
holds no \verb|none|: \verb|settings.get("note")| is then
\verb|none|, as for a member that was never written.

The checker cannot know what a text that arrives later will hold, so
what \verb|json.parse| gives has no type it knows. Everything can be
asked of it, and a mistake is found when the line runs. Say the type
where a value leaves the JSON, as \verb|let limit: int| does above,
and the rest of the program is checked as usual. For the same reason
\verb|json.parse| is refused in strict mode and in a build: JSON is for
\verb|zeno run| and for a web page.

\verb|json.write| takes the same values, and objects, which it writes
field by field in the order the class declares them. That is how a
program writes JSON with text in one member and a number in the next:
a class says which, and the checker holds every object to it.

\begin{zeno}[file=order.zeno, dir=json]
import json

class Line {
    item: str
    count: int
}

class Order {
    who: str
    lines: list[Line]
    note: str or none
}

print(json.write(Order("Ada", [Line("tea", 2), Line("milk", 1)], none)))
print(json.write(["volts": 3.3, "amps": 0.5]))
\end{zeno}

A quantity is refused, because JSON has no units and a reader could
not tell that \verb|3.3| was volts: write the number, and put the unit
in the name, as above. Text that is not JSON raises a
\verb|ValueError|.

\begin{summary}
\verb|print| writes a line. \verb|input()| reads one, and gives
\verb|none| when there are no more. \verb|program.arguments()| gives
the words after the file. \verb|files.read|, \verb|write|,
\verb|append|, \verb|exists| and \verb|remove| work on whole files of
text, and every one but \verb|exists| may raise a \verb|FileError|,
which can always be caught. \verb|files.read_bytes| and
\verb|write_bytes| work on a file as its bytes, in a \verb|list[u8]|.
\verb|files.list| gives the names in a folder, sorted, and
\verb|files.make_folder| makes one; \verb|files.join| puts a path
together. \verb|files.read_from|, \verb|write_to| and
\verb|append_to| open a file to be read or written in pieces, and it is
closed when its owner ends. \verb|json.parse| and \verb|json.write| read and write
JSON.
\end{summary}
