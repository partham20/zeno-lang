\chapter{Compiling}\label{ch-compiling}

\verb|zeno run| reads a program and does what it says, a piece at a
time. \verb|zeno build| turns the same program into C, and the
machine's C compiler turns that into a program of its own: no Zeno
needed to run it, and many times faster. The C can also be compiled for
a microcontroller, which is where Zeno is going.

\section{zeno build}

\begin{zeno}[file=primes.zeno, cmd=zeno build {file} ;; ./primes]
function is_prime(n: int) -> bool {
    if n < 2 {
        return false
    }
    var d = 2
    while d * d <= n {
        if n % d == 0 {
            return false
        }
        d += 1
    }
    return true
}

var count = 0
for n in range(200000) {
    if is_prime(n) {
        count += 1
    }
}
print(count, "primes below 200000")
\end{zeno}

\verb|zeno build| wrote \verb|primes.c|, called the C compiler on the
machine (\verb|cc|, which is usually GCC or Clang), and left the
program \verb|primes| beside it. On the computer this book was built
on, \verb|zeno run| takes about two seconds over it, \verb|zeno run --vm|
 about one, and \verb|./primes| a fiftieth of a second.

\section{Reading the C}

The C file is kept, and it is meant to be read beside the Zeno. Here
is \verb|is_prime|:

\begin{zeno}[file=primes.zeno, show=no, cmd=zeno build {file} > /dev/null ;; grep -A12 "^static bool z_is_prime(int64_t z2_n) {" primes.c]
function is_prime(n: int) -> bool {
    if n < 2 {
        return false
    }
    var d = 2
    while d * d <= n {
        if n % d == 0 {
            return false
        }
        d += 1
    }
    return true
}

var count = 0
for n in range(200000) {
    if is_prime(n) {
        count += 1
    }
}
print(count, "primes below 200000")
\end{zeno}

It is the Zeno, line for line. An \verb|int| is an \verb|int64_t|.
\verb|d * d| is \verb|zeno_mul|, which checks for overflow with the
compiler's own built-in and raises an \verb|OverflowError| with the
line and column (the two numbers after the operands) when the answer
does not fit. A C compiler that is neither GCC nor Clang has no such
built-in, and gets the same check written out in plain C. In front of the program stands Zeno's runtime, a small
C library for text, lists, errors and \verb|print|, pasted into every
file so that the C needs nothing else to compile.

\begin{why}
C runs on every processor there is, and every microcontroller vendor
ships a C compiler for its chips. Writing C first gave Zeno all of them
at once, and C that a person can read is a C that a person can check.
(Decisions 5.5 and 5.5b.)
\end{why}

\section{Build agrees with run}

A program must print the same whichever way it is run: \verb|zeno run|,
\verb|zeno run --vm|, a C build, an LLVM build, a firmware build.
Errors included: an uncaught error gives the same message, at the same
line and column, in every one. Zeno's own tests run every test program
every way and compare the output byte for byte.

\begin{why}
A program that behaves one way under test and another on the board is
the worst kind to debug. If \verb|zeno run| is to be the place where
firmware is tried, it must mean exactly what the compiled program
means. (Decision 5.5d.)
\end{why}

\section{A build is strict}

\verb|zeno build| always checks in strict mode: every type must be
known, because a compiled program has no tags to carry them
(\hyperref[ch-types]{Types, Written and Worked Out}). A program that
runs with dynamic values under \verb|zeno run| is told which value is
the trouble:

\begin{zeno}[file=loose.zeno, cmd=zeno build {file}, fails=yes]
function same(x) {
    return x
}
print(same(1), same("one"))
\end{zeno}

\section{The options}

Option & Means \\

\begin{zeno}[file=lists.zeno, cmd=zeno build --memory {file} ;; ./lists]
var squares: list[int] = []
for n in range(1000) {
    squares.append(n * n)
}
print(len(squares), squares[999])
\end{zeno}

\section{The least C}

The C that \verb|zeno build| writes keeps every promise Zeno makes,
and that takes room. Each sum is checked, each index is checked, each
error can say its line, and the whole runtime stands in front of the
program in case it is needed: about 4,500 lines of C for a program of
one line. Once a program is correct, \verb|--minimal| writes the
other kind of C: the least that runs it, close to what a person would
write by hand.

\begin{zeno}[file=multiples.zeno, cmd=zeno build --minimal {file} ;; ./multiples ;; grep -c "" multiples.c ;; grep -A18 "^static int64_t z_total" multiples.c]
function total(limit: int) -> int {
    var sum = 0
    for n in range(limit) {
        if n % 3 == 0 {
            sum += n * 2
        }
    }
    return sum
}

print(f"the total is {total(1000)}")
\end{zeno}

The number after the answer is how many lines the C file has, and the
rest is the program, whole. \verb|n * 2| is C's own \verb|*|, with
nothing checking it. \verb|print| is \verb|printf|. No call ends in
a line and a column. Of the runtime, one function is left, a few lines
above \verb|z_total| in the file: \verb|zeno_mod|, because
\verb|-7 % 3| is 2 in Zeno and $-1$ in C, and that is not a check but
what \verb|%| means.

What is given up is every check. In a minimal build a mistake does
what it would do in C:

\begin{center}
\begin{tabular}{P{4.6cm}P{3.2cm}P{4.6cm}}
\toprule
 & \verb|zeno build| & \verb|zeno build --minimal| \\
\midrule
an index out of range & \verb|IndexError| & reads or writes whatever memory is there \\
a key the dict does not have & \verb|KeyError| & reads an item that is not there \\
a whole number that overflows & \verb|OverflowError| & no defined result \\
a whole number divided by zero & \texttt{Zero\-Division\-Error} & what the processor does; on a computer the program is stopped \\
a float divided by zero & \texttt{Zero\-Division\-Error} & infinity, or NaN \\
\verb|u8(300)| & \verb|ValueError| & 300 goes on as it is \\
an error nothing catches & says what, and the line & says what \\
\bottomrule
\end{tabular}
\end{center}

What is kept is everything a correct program can meet.
\verb|int("ten")| still raises a \verb|ValueError| and a file that is
not there a \verb|FileError|, \verb|try| and \verb|except| work as
they did, and the program prints what it printed before, to the last
digit of a float.

\verb|--minimal| goes with \verb|--firmware|, \verb|--owned| and
\verb|--no-collector|. A program that makes a list still needs
something to free it, and the garbage collector is some 500 lines of
C that no option makes small, so the smallest C for such a program
comes from \verb|--minimal --no-collector|. The file gets much
smaller, 23 lines for a program that prints one line; the program the
C compiler makes of it gets a little smaller, since the C compiler
never put an unused function into it in the first place.

\begin{why}
Two readers want two things from the C. While a program is being
written, the C should stop at the first mistake and say where. When it
is done and its C is to be read, reviewed or carried into another
project, every line that is not the program is in the way. So there
are two builds, and the one that checks is the one you get without
asking. (Decisions 30.1 to 30.12; \verb|docs/minimal.md| has the whole
table and the sizes.)
\end{why}

\section{Through LLVM}

\verb|zeno build --llvm| writes the program in LLVM's intermediate
language, the one Clang, Rust and Swift compile through, and hands it
to \verb|clang|. The program is the same, and prints the same:

\begin{zeno}[file=primes.zeno, show=no, cmd=zeno build --llvm {file} ;; ./primes]
function is_prime(n: int) -> bool {
    if n < 2 {
        return false
    }
    var d = 2
    while d * d <= n {
        if n % d == 0 {
            return false
        }
        d += 1
    }
    return true
}

var count = 0
for n in range(200000) {
    if is_prime(n) {
        count += 1
    }
}
print(count, "primes below 200000")
\end{zeno}

The IR is written as text by Zeno itself, with no LLVM library, and
\verb|primes.ll| can be read like \verb|primes.c|. LLVM brings its own
optimiser and every processor it knows. \hyperref[ch-inside]{Inside
Zeno} shows a piece of it.

\section{For another processor}

\verb|zeno build| compiles for the computer it runs on. A
microcontroller has a C compiler of its own, flags that say which
processor it is, a file that runs before \verb|main|, and a linker
script that says where its flash and RAM are. Those four are the same
for every program on one board, so they are written down once, in a
folder, and \verb|--board| names the folder:

\begin{zenofrag}[lang=shell]
$ zeno build --board boards/qemu-cortex-m3 blink.zeno
Wrote blink.c
Built blink.elf for the board in `boards/qemu-cortex-m3`.
Run it with: qemu-system-arm -M lm3s6965evb -nographic -kernel blink.elf
\end{zenofrag}

The folder has a file called \verb|zeno.board|, read as a
\verb|zeno.package| is. Each word in quotes is one word of the command
the compiler is given:

\begin{zenofrag}[lang=shell]
about "An ARM Cortex-M3 that QEMU emulates"

compiler "arm-none-eabi-gcc"
flags "-mcpu=cortex-m3" "-mthumb"
sources "startup.c" "system.c"
script "link.ld"
link "-nostartfiles" "-Wl,--gc-sections"
run "qemu-system-arm" "-M" "lm3s6965evb" "-nographic" "-kernel"
\end{zenofrag}

(The board's real \verb|run| line has one more word,
\verb|"-semihosting"|, which lets the program tell QEMU that it has
ended.)

\verb|compiler| is the one line a board must have. \verb|header| names
the header with the board's own functions
(\hyperref[ch-firmware]{Firmware}); a board without one, like this
one, has the simulated pins. \verb|zeno build| shows the \verb|run|
command and does not run it: on a real board it writes to the chip.

The program is built as \verb|--no-collector| builds it, because the
garbage collector takes its memory 64 KB at a time and this chip has
64 KB in all. \verb|--minimal|, \verb|--release|, \verb|--fast| and
\verb|--memory| go with \verb|--board|.

The board in the example comes with Zeno, in its repository, and needs
no hardware: QEMU emulates an ARM Cortex-M3 with 256 KB of flash and
64 KB of RAM. Every example in this book that a build with no
collector accepts is built for it and compared with the same program
on a computer, each time the compiler changes. No program of Zeno's
has run on a real board yet.

Beside it is a second folder for the same chip,
\verb|boards/lm3s6965evb|, which has a \verb|header| line. There a pin
is a bit of one of the chip's ports and not a line of text, and
\verb|print| goes out of the chip's serial port through four functions
of the header (\hyperref[ch-board]{The Board}), with no \verb|printf|
and no \verb|exit| under the program:

\begin{zenofrag}[lang=shell]
$ zeno build --board boards/qemu-cortex-m3 hello.zeno
$ arm-none-eabi-size hello.elf
   text    data     bss     dec     hex filename
   8096    1376     380    9852    267c hello.elf
$ zeno build --board boards/lm3s6965evb hello.zeno
$ arm-none-eabi-size hello.elf
   text    data     bss     dec     hex filename
    920      16       4     940     3ac hello.elf
\end{zenofrag}

A number with a fraction is made into text by Zeno's own runtime on
both boards, with whole numbers. The C library's \verb|snprintf| would
be 28 KB of this chip's flash, and the runtime's digits are 1 to 4.

\begin{why}
Building C for a target is a job the target's own tools already do
well, with the flags, linker scripts and start-up code that only they
know. So Zeno copies none of them. A board's folder names the tools an
engineer already has, and Zeno types the one long command that was
typed by hand before. The flags are in a folder of the board's and not
in the program's package, because one program is built for two boards
and one board runs many programs. (Decisions 5.12c and 51; new in
0.7.)
\end{why}

\section{What does not compile yet}

Nearly the whole language compiles. A few corners do not, and
\verb|zeno build| names each one and points at the line, while
\verb|zeno run| still runs the program:

\begin{zeno}[file=named.zeno, cmd=zeno build {file}, fails=yes]
function area(width: int, height: int) -> int {
    return width * height
}
let measure = area
print(measure(height = 2, width = 3))
\end{zeno}

The type of a function value has no names for its parameters, so a
build cannot know which argument is which; \verb|zeno run| reads them
off the function the variable holds. Passing them in order builds.
The table in \verb|docs/compiler.md| lists every such corner with its
reason, and a test holds the compilers to it. Since 0.8.0 a function
with a name written inside another, a default worked out at the call,
a method used as a value and a function value that raises all build;
\hyperref[app-limits]{Appendix G} has what is left.

A program that uses the library of another language through
\verb|import python| or one of its like is refused too, because a
built program must run where that language may not be
(\hyperref[ch-other-languages]{Libraries of Other Languages}). A
library of C is the other way round: a build calls it directly and
links it in, on a board as well (\hyperref[ch-c-libraries]{Libraries
of C}).

\section{In another language (new in 0.5)}

\verb|zeno build --target| writes the program in another language: a
file you can read, keep, and run with that language's own tools. The
languages are \verb|js| (JavaScript, for Node), \verb|ts|
(TypeScript), \verb|html| (a page that runs the program), \verb|py|
(Python), \verb|php|, \verb|go|, \verb|java|, \verb|cs| (C\#),
\verb|cpp| (C++), \verb|rust|, and \verb|wasm| (WebAssembly, built
through Rust). Zeno 0.5.2 added four: \verb|lua|, \verb|ruby|,
\verb|dart| and \verb|kotlin|.

\begin{zeno}[file=area.zeno, cmd=zeno build --target js {file} ;; node area.js ;; zeno build --target py {file} ;; python3 area.py]
import math

function area(r: float) -> float {
    return math.pi * r * r
}
print(area(2.0))
\end{zeno}

The file is written by fixed rules, so the same program always gives
the same file, letter for letter. Each language gets a runtime of its
own, at the top of the file, which does what \verb|zeno run| does, step
for step: an \verb|int| still overflows in JavaScript, whose numbers
never do, and in Python, whose whole numbers never stop growing.

\begin{zeno}[file=area.zeno, show=no, cmd=zeno build --target py {file} > /dev/null ;; grep -A6 "^def main" area.py]
import math

function area(r: float) -> float {
    return math.pi * r * r
}
print(area(2.0))
\end{zeno}

\verb|Z.mul(a, b, 4)| multiplies as Zeno multiplies, and stops with
Zeno's message for line 4 if the answer does not fit. \verb|math| is
\verb|math_| because \verb|math| is a name the languages' own libraries
use.

As with \verb|zeno build| itself, a tool holds every target to
\verb|zeno run|: \verb|tools/targets.py| runs every example and every
sample of this book in every language and compares what each prints,
and it runs once a week on the newest version of each language.

A program that uses the board, \verb|unsafe| or manual memory is
refused: those belong to a program compiled to machine code. The page
cannot use the keyboard or files, or \verb|sleep|.

\begin{why}
A program you have written in Zeno can then live where another language
lives: on a web page, in a Python project, on a Java server. And it is a
way to learn: the same program, written by fixed rules in fifteen
languages, shows what each language needs said that Zeno does not.
(Decisions 24.1 to 24.34; \verb|docs/targets.md| has every target.)
\end{why}

\begin{summary}
\verb|zeno build| writes C, compiles it with the machine's compiler,
and keeps both. The compiled program prints what \verb|zeno run|
prints, errors included, and is many times faster. A build is always
strict. \verb|--llvm| goes through LLVM; \verb|--memory|,
\verb|--firmware| and \verb|--no-collector| are for the board. For
another processor, the C goes to that processor's compiler.
\verb|--minimal| writes the least C for a program that is already
correct, with no checks in it.
\verb|--target| writes the program in another language instead.
\end{summary}

\begin{tryit}
\begin{enumerate}
\item Build a program from an earlier chapter, open its C file, and
  find each of your functions in it.
\item Time \verb|zeno run|, \verb|zeno run --vm| and the built program
  on the primes example, with a larger limit.
\item Make a program overflow an \verb|int| and build it. Is the message
  the same as \verb|zeno run|'s?
\item Build with \verb|--llvm|, open the \verb|.ll| file, and find
  \verb|is_prime|.
\item Build the primes example with \verb|--minimal| and read the
  whole of \verb|primes.c|. Then read a list past its end in a small
  program, and build that both ways.
\item Build the area example with \verb|--target go| and
  \verb|--target java|. Find \verb|area| in each, and compare the two
  with the Python.
\end{enumerate}
\end{tryit}
