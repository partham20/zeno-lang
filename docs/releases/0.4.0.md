Zeno 0.4 has a way to build that is as fast as C and Rust,
`zeno build --fast`, and it mends what the release of 0.3.0 found on
macOS.

## `zeno build --fast`

A new way to build, for a program whose tests pass, when every last bit
of speed matters. It leaves out the checks a correct program never
fails, as C does: a list index out of range, a float divided by zero,
the square root of a number below zero, and the overflow of a whole
number. The C compiler is asked for `-O3`. Every other build keeps all
its checks.

Overflow is where it differs from `--release`. With `--release` a sum
that overflows wraps round. With `--fast` it has no defined result, as
in C, and the C compiler builds on its not happening. That is what
makes a loop of whole numbers the same instructions a C program gets:
on the loop benchmark `--fast` runs 300.27 million instructions where C
runs 300.26 million. An overflow is an error in Zeno, so a program that
runs clean under `zeno run` has none (docs/memory-modes.md, decision
23.6).

On the six benchmarks, counted in instructions, `--fast --owned` runs
no more than C on five of the six, far fewer on two of them, and 6%
more on the sixth (fib, where the time is the same); the times are in
bench/README.md. Rust is ahead on one, nbody, because its compiler
knows there are exactly five bodies; with the number hidden from it,
it is behind both C and Zeno (decision 23.4).

## Faster in every build

- A number becomes text (`str(n)`, `{n}`) several times faster, without
  `snprintf`.
- In an owned program, a big list grows with `realloc`, as a C array
  does, instead of being copied each time it doubles.
- `x // 8` and `x % 8`, by 2, 4, 8 and so on written as a number, are
  one shift and one mask, with nothing to check. `%` and `//` by any
  other number take fewer instructions than they did (decision 23.5).
- `xs.append(x)` is a compare, a store and a count in the loop that
  appends, not a call (decision 23.8).

## Benchmarks that can be trusted to one in a hundred

`python3 bench/run.py --count` counts the instructions each program
runs, under valgrind. The count is the same on every run, where a time
on a busy machine moves by a tenth. Timed runs now go in rounds, each
engine once per round. Both sets of numbers are in bench/README.md
(decision 23.7).

## The two generations of the collector, on macOS too

0.3.0 had the collector's two generations on Linux only: on macOS they
made programs built with `zeno build --llvm` hang. The cause is found
and mended (see below), so a program built on macOS now has them too,
and most of its collections look only at the blocks made since the
last one. On Windows every collection still looks at everything.

## Mended

- On macOS, in a program built with `zeno build --llvm`, catching an
  error with `try` could leave signals held back from then on: Ctrl-C
  no longer stopped the program. A `try` remembered its place in one
  way and `raise` went back to it in another, and the two did not
  agree about signals. This was in 0.2.0 and 0.3.0. Programs built
  with plain `zeno build` were right.
- The release of 0.3.0 left `packaging/arch/.SRCINFO` in the
  repository at 0.2.0, beside a `PKGBUILD` of 0.3.0. A release now
  keeps both.
