These are the notes of Zeno 0.8.0 as far as it has come. It is not
released: this page is written as the work reaches `main`, and is
finished on the day of the release.

Zeno 0.8.0 is to take items 9 to 14 of
[docs/missing.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/missing.md),
the list of what Zeno lacks: what a build with no collector still
refuses and `raises` in a function type, several values from one
function, generic enums and interfaces with bounds, cleaning up when a
block ends and files read in pieces, tools, and more than one thing at
a time.

## `raises` in a function type

A function type can say what a function of that type raises, as the
function's own first line does: `function(str) -> int raises
ValueError`. A call through such a value is checked as a call of the
function by its name, so its caller catches the error or says
`raises` itself. A function fits the type if `except ValueError` would
catch what it raises, and `raises Error` takes any. A firmware build
and a build with no collector used to refuse `texts.map(parse)` where
`parse` raises; they build it now, and print what `zeno run` prints.
A function that returns a raising function writes that type in
brackets, `-> (function(int) -> int raises ValueError) raises
Missing`, since `raises` after a result has always belonged to the
function it ends. See
[docs/raises-in-types.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/raises-in-types.md)
and chapter 56 of the decisions. After `raises`, `or none` needs the
brackets too, since `function() raises ValueError or none` could be read
as raising `ValueError` or nothing.

## A function that is kept takes what it uses

A function written where a value goes, which is returned, put in a
variable or a field, or given to a parameter that says `take`, now
takes each value with one owner that it uses, as `let b = a` would,
and frees them when it is freed. A build with no collector refused
such a function before, so `compose(f, g)` could not be written there;
it builds now. A function only passed along, to `map` or a parameter
that looks, looks as before. It cannot take a `var`, in any build:
the `var` could be given a new value after it was taken, and the
message says to declare it with `let`. With no collector, a function called
straight from the call that made it, as in `make(2)("5")`, is freed at
the end of its line; 0.7.0 left it. See
[docs/kept-functions.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/kept-functions.md).

## A method used as a value

`let m = counter.bump` builds with both compilers, in every build. It
is the function that calls the method: passed along, it looks at
`counter`, and kept, it takes it where `counter` has one owner. It is
bound to the object `counter` holds on that line, as `zeno run` binds
it. 0.7.0 ran it with `zeno run` and refused it in every build. See
[docs/method-values.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/method-values.md).

## `take` in front of a field or an item

`let task = take slot.task` gives what the field holds and leaves
`none` there; `take tasks[i]` does the same for an item of a list. The
place must be one that may hold `none`. It means the same in every
build, and with one owner it is how an object hands on what it holds,
which it could not do before. `take` was a reserved word already, so
nothing that built before changes. See
[docs/take.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/take.md).

## A value with one owner in a generic

With no collector, a list or an object can now fill a type parameter:
`Stack[Frame]`, `Box([1, 2])` and `same(frame)` build, and the copy is
checked as a class or function written by hand for that type would be.
`take T` says that a generic keeps what it is given, and is right for
a number too. See
[docs/generic-owned.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/generic-owned.md).

## A dict that owns its values

With no collector, a dict can now hold lists and objects:
`dict[str, Channel]` builds, and the dict owns its values as a list
owns its items. `d[key]` looks, a store over a key frees the value
that was there, `pop(key)` hands it over, and `clear` and the end of
the dict free every value. `get(key, instead)` and `values()` are
refused there, with what to write instead. See
[docs/dict-owned.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/dict-owned.md).

## A list of numbers that may be `none`, with no collector

With no collector, `list[int or none]`, `list[float or none]` and the
rest now build. The list owns a small block of the pool for each
number, as it owns its copy of each text, and `none` takes none: a
store frees the old block, `pop` and `take` free the one they read
out, and `clear` and the end of the list free every one. Each number
costs a block of the pool, so on a small board a plain list with a
number that stands for "nothing", or an enum with a `Missing` case, is
still the cheaper list. See
[docs/none-list.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/none-list.md).

## The size of the pool on the command line

`zeno build --no-collector --pool 4096` and `--text-room 2048` set the
size of the pool and of the text room, which until now took a flag
for the C compiler by hand. They go with `--board` and `--llvm`, and
are refused, with the reason, where there is no fixed pool. With
`--memory` and no collector, a block that is given back is filled,
and a write to it before it is handed out again stops the program
with a message: the check the heap checkers of C cannot make inside
the pool. Without `--memory` the C is what it was. See
[docs/pool-size.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/pool-size.md).

## A function inside a function, and a default that is worked out

`zeno build` now takes a function with a name written inside a
function, and a default that is more than a literal, through C and
LLVM, with or without a collector. One that uses nothing of the
function around it becomes a function of the file, so it can be called
above its line; one that does is made once, after the last thing it
uses. A default is worked out at each call that leaves its argument
out, reading the parameters before it and the file's names. See
[docs/inner-functions.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/inner-functions.md).

## Fixed

A function that tested a parameter that may be `none` and then read a
field of it read the field before the test in every build of C and
LLVM of 0.7.0, and so read through `NULL` when given `none`. It reads
it after the test now.

Everything a program wrote for 0.7.0 means what it meant.
